# AGENTS.md

Windows-only C#/.NET 10 WPF launcher for FiveM. Design decisions and UX philosophy live in `DOC.md` (in English); commit messages are English conventional commits. UI strings and documentation are English. Development is strictly TDD (RED -> minimal implementation -> GREEN -> REFACTOR), one layer at a time. The refactor step is mandatory: after every GREEN, improve the code — enforcing DRY, KISS, SOLID and YAGNI — with the suite still green, before starting the next test.

## Commands
- Build: `dotnet build FiveMServerLauncher.slnx`
- Test all: `dotnet test`
- Run one test class: `dotnet test --filter FullyQualifiedName~CfxServiceTests` (xUnit)
- Publish portable single-file win-x64 (`CFXLauncher.exe`, self-contained, one file; native
  WPF libs self-extract to temp at startup). First build, then publish with `--no-build` (a
  publish that recompiles WPF markup in the `_wpftmp` temp project cannot resolve the
  Grpc.Tools-generated `Master` types — CS0246). `-r win-x64` alone does NOT imply
  self-contained (.NET 8+ breaking change), and a framework-dependent build output reused by
  `--no-build` would publish without the runtime — so `SelfContained=true` is mandatory at
  BUILD time:
  `dotnet build src/FiveMServerLauncher/FiveMServerLauncher.csproj -c Release -r win-x64 -p:SelfContained=true`
  `dotnet publish src/FiveMServerLauncher/FiveMServerLauncher.csproj -c Release -r win-x64 --self-contained --no-build -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -p:DebugType=none -p:DebugSymbols=false -o dist`
  Single-file props stay on the command line, never in the csproj. Compression (`EnableCompressionInSingleFile`)
  drops the deliverable from ~140 MB to ~62 MB with zero runtime risk; IL trimming is NOT used
  (runs at build time, which the `--no-build`/`_wpftmp` constraint forbids, and WPF is reflection-heavy
  so trimming risks runtime breakage — that's why `PublishTrimmed=false` stays in the csproj).
- Solution uses the new `.slnx` format: `dotnet sln FiveMServerLauncher.slnx add <project>`.
- Requires .NET 10 SDK. Verify with `dotnet --version` before running anything.

## Architecture
- `Core/Enums`: shared types. `GameClient` = FiveM | FiveMEnhanced | RedM. Note `DOC.md` lists only two — the code is source of truth; `Service/CfxService.cs` maps CFX `gamename` (`gta5`, `gta5enhanced`, `rdr3`) to it.
- `Configuration/`: global launcher settings only. `LauncherSettings` is `PreferredClient` + `AutoLaunch` + `LastServerAddress` (the "open automatically next time" memory — the last successfully launched connect address) + `Language` (v1.2; nullable language tag for UI localization, null = follow the system language, applied live via the `ILocalizer` seam wired in `App.xaml.cs`) + `DevGameBuild` / `DevPureMode` (persisted Dev Mode values; the dev client toggle and `-cl2` are session-only, never persisted). JSON persistence via `ISettingsStorage` -> `FileSettingsStorage` (System.Text.Json + `JsonStringEnumConverter`, `launcher-settings.json` next to the running exe via `PortableDataDirectory`; `IOException` (AV sharing locks) and `JsonException` both degrade to defaults, never crash startup). Never add per-server fields, `Platform`, or `ServerPort` here.
- `Domain/SavedServer` (immutable, private ctor + validated `Create`, `[JsonConstructor]` for persistence) carries `Name`, `Address` (trimmed, classified connectable via `ServerAddress.Classify`), manual `RequiresSteam`/`RequiresDiscord` (`bool?`), optional `CfxId` (enrichment key, null when unknown; derived from CFX-form addresses, or captured at save time for IP:port/domain), and `MatchesAddress` (case-insensitive identity key). `Configuration/IServerRepository` -> `FileServerRepository` persist the saved-servers JSON list (missing/corrupt/invalid entries → empty, never crash — `ReadAllText` sits inside the sanctioned catch set, so `IOException` (AV sharing locks) and `JsonException` both degrade; missing `CfxId` in old files → null; `Add` rejects duplicates, `Update` is address-keyed, `Remove` no-ops when unknown, `Move(address, newIndex)` is a position-only reorder (never rewrites record fields, so a background cfx-id capture can never be clobbered), `Replace(address, replacement)` swaps a record in place across an address-changing edit); tests use `InMemoryServerRepository`.
- `Domain/GameBuilds` (pure, static) is the game-build option engine: `Options(game, storedBuild, noneLabel, data = null)` (null data → the curated `Baseline`) and `SupportsBuildSelection(game)` (FiveM/RedM — the shared gate behind both the engine's empty Enhanced list and the dialog combo's `IsDialogGameBuildEnabled`). `GameBuildData(FiveM, RedM, Names)` is pure data, so the baseline and a runtime-fetched dataset are interchangeable by construction. `Service/GameBuildDataService` (seam, `HttpClient`) builds that dataset once per session: numbers replace (all-or-nothing — a premake section empty or garbage → null → the UI keeps the baseline), names merge (fetched wins over baseline; any names-side failure → baseline names while numbers still refresh). Never throws: outage swallows `HttpRequestException`/`TaskCanceledException`, and parse guards (`int.TryParse` both parsers) make drifted input skip entries instead of throwing.
- `Service/ServerEnrichmentService` (seam, `IServerEnrichmentService`; `HttpClient` + `ServerCatalog` + optional `IDnsResolver`) powers the enriched saved-server rows: `RefreshAsync(bool forceRefresh = false)` maps the streamRedir catalog snapshot to a `CfxId → ServerPresence(Online, Players, MaxPlayers, Game, IconVersion)` dictionary (`null` = outage, never throws; duplicate EndPoints grouped; `gamename` var → `GameClient` via `CfxVars`, and `IconVersion` from the catalog's typed `iconVersion` proto field — field 11, never a var; zero = no icon, any non-zero value including negative is a valid icon version, and a version that unexpectedly 404s degrades to a null icon in the download step) — the forced variant bypasses the catalog TTL and is rate-limited by a shared injectable cooldown (`DefaultForceCooldown` 15 s; refused forces fall back to the TTL path), `GetIconAsync(cfxId, iconVersion)` downloads + caches the PNG bytes keyed by `(CfxId, iconVersion)` with single-flight per key (the in-flight task is registered *before* the download starts, so a synchronously completing download can never park a completed task as in-flight and serve stale bytes after an eviction), an injectable concurrency bound (`maxConcurrentIconDownloads`, default 4) and an LRU-bounded icon cache (`maxCachedIcons`, default 256, via the shared `Service/LruCache`) — there is NO `/single/` version-probe path: the catalog snapshot's typed `iconVersion` field (never a var — a var-based lookup matches nothing in the real payload and made icons disappear; see ticket 10) is the single proof of presence/absence, and `ResolveCfxIdAsync(address)` returns the catalog `EndPoint` (= canonical cfx id) for all connectable forms — CFX forms extract directly; IP:port/domain and the port-less forms use the catalog's matching rules (host match, DNS, `:30120` fallback); all outages degrade to null/empty, never throw (swallows `HttpRequestException`/`TaskCanceledException` only; an unexpected fault propagates to every caller sharing the in-flight download).
- **Composition root**: `App.xaml.cs` `OnStartup` first enforces single-instance via `Service/SingleInstanceGuard` (`ISingleInstanceLock` = `MutexSingleInstanceLock` named `Local\CFX Launcher.SingleInstance`; `IExistingWindowActivator` = Win32 restore+foreground by window title — duplicate exits silently via `Shutdown()`) and only then builds the object graph manually (`HttpClient` → shared `ServerCatalog` → `CfxService`/`ServerEnrichmentService` → `ServerResolver` → `GameLauncher` (`GameProcessLauncher` + `ProcessStarter` + `UriSchemeRegistration`, `CitizenFxPreparer` + `ClientInstallLocator` + `CitizenFxConfigWriter`; the same `ClientInstallLocator` instance is shared with `GameLauncher` and `MainViewModel`) → `ExternalAppStarter`/`ExternalAppPreparer` (shared `ProcessReadinessChecker`) → `GitHubReleaseFeed` (shared client; small JSON) + `UpdateApplier` (dedicated 10-minute download client, `Environment.ProcessPath` provider, `ProcessStarter`, the single-instance guard as the released lock, `Shutdown` as the exit action) → `MainViewModel`) and sets `MainWindow.DataContext`; no DI container, no `StartupUri` in `App.xaml`. It also starts the per-minute enrichment loop on the window dispatcher (cancelled when the window closes); a single `ServerCatalog` is shared between `ServerResolver` and `ServerEnrichmentService` so the streamRedir cache is not duplicated.
- `Launch/` (Application layer; named `Launch` to avoid clashing with `System.Windows.Application` in WPF): `GameLauncher.ConnectAsync(ServerProfile)` primes the Legacy FiveM client config (`ICitizenFxPreparer.PrimeAsync`; best-effort, never throws, never fails the connect, and a throwing preparer is also swallowed by GameLauncher so the `LaunchResult` stays exact), builds `FiveMLaunchOptions` and returns a `LaunchResult` — a sealed record hierarchy (`Connect(Uri)` after delegating the `fivem://connect/...` URI to `IGameProcessLauncher` the process seam, `OpenClient(GameClient)` when the client process was started, `NotInstalled(GameClient)` when no executable resolves, or `StartFailed` on launch exception; no null-union — the type IS the discriminator). When the profile has no URI (e.g. `FiveMEnhanced`), `ConnectAsync` invokes the same open primitive: `GameLauncher.OpenAsync(GameClient)` resolves the executable via `IClientInstallLocator`, starts it through `IGameProcessLauncher.StartExecutableAsync(path)` (a second overload takes CLI args — used by Dev Mode with `UseShellExecute = true`, i.e. ShellExecute-with-args after the single-parameter `fivem://<flag>` route proved insufficient), and reports `OpenClient`/`NotInstalled`/`StartFailed`. `GameLauncher.OpenAsync(FiveMLaunchOptions)` is the Dev Mode entry: serializes `ToCommandLineArgs()` (`-b<build> -pure_<n> -cl2`), resolves the Legacy exe via the locator, starts with args. `Launch/CitizenFxPreparer` owns the "what+when to write" decision for `CitizenFX.ini`: only CFX-validated Legacy FiveM or RedM profiles, `DefaultBuild` from `sv_defaultGameBuild` when `> 0` (else `sv_replaceExeToSwitchBuilds` → `sv_enforceGameBuild`) and `PoolSizesIncrease` verbatim when non-blank — else the key is reset to an empty value so default-pool servers clear stale increases. Real launch is `Launch/GameProcessLauncher` (real `IGameProcessLauncher`): throws `Win32Exception` when the `fivem://` scheme is unregistered (`IUriSchemeRegistration` seam, so `StartFailed` stays reachable; the real `UriSchemeRegistration` disposes the opened registry key), then hands the URI to the Windows shell via `explorer.exe` (`IProcessStarter` seam; `CreateProcess`, no direct `ShellExecuteEx`; the real `ProcessStarter` disposes the `Process.Start` wrapper — disposing it never kills the started process); direct executable opens go the same shell route (`explorer.exe "<path>"`) — both need shell context (Rockstar/GTA launcher refuses a loader-started child). Shell context is required: `ShellExecuteEx` of the `fivem://` URI direct from the launcher process made FiveM's GTAVLauncher legit flow refuse the GTA boot ("This application should be launched directly from the shell or a web browser") — the URI itself is correct and manual Win+R/`Start-Process` launches work. The scheme-check + shell-launch is shared by
           `GameProcessLauncher`/`ExternalAppStarter` via `Launch/UriShellStarter` (internal helper). `Launch/ExternalAppStarter`
           (real `IExternalAppStarter`) opens a required external app through its URI scheme (`steam://`/`discord://`); an
           unmapped `ExternalApp` value is a no-op (totality guard mirroring `ProcessReadinessChecker`). `Launch/ExternalAppPreparer`
           (`IRequirementReadiness` + `IExternalAppStarter`, injectable wait + `maxAttempts`; defaults 500 ms / 120 ≈ 60 s) is the
           "start the missing required app and wait until it is **ready**" open+check loop: already ready → `true` without touching
           it, else start only when the process is not running, then poll readiness (immediate check first, then wait between
           checks); an app that is *already running but not ready* (e.g. Steam at the login screen) is waited on **without
           restarting**; readiness/start/wait exceptions all degrade to `false`, never throws to the caller.
- `ViewModels/` (MVVM layer): `MainViewModel` (ServerAddress/IsBusy/StatusText/ConnectCommand) drives the connect flow; uses `ServerResolver` + `GameLauncher` + `IServerRepository` + `ExternalAppPreparer` + `IClientInstallLocator` + `ConfigurationRepository` + `IServerEnrichmentService`; matches the typed address to a saved server, resolves (effective requirements), and *prepares every required app* through the preparer (which is a no-op when the app is already ready): for each required app it shows "Starting {app}..." then prepares it — starting the process if absent and waiting until it is *fully ready* (logged in for Steam) — giving up with "Could not start {app}" (no launch) when an app can't be prepared; nothing extra when nothing is required or all are already ready; catches `InvalidAddressException` → "Invalid address" (English UI strings; see migration phase). The VM merges the loaded `LauncherSettings` into itself (`_settings`): `AutoLaunch`/`PreferredClientOption` setters save through the repository immediately, and a successful connect persists the trimmed address as `LastServerAddress` (failures never clobber it). It also owns the direct-open flow: `InitializeAsync` seeds `AvailableOpenClients` from the install locator (FiveM Legacy, then FiveM Enhanced, then RedM; installed only), `SelectedOpenClient`/`SelectedOpenClientLabel` drive the OPEN button, `SelectOpenClientCommand` changes the selection, and `OpenClientCommand` opens the selected client through `GameLauncher.OpenAsync`; connect and open share a `Describe(LaunchResult)` status mapping ("Opening {client}...", "{client} is not installed", "Launch failed"). Display names live in `InstalledClientOption` ("FiveM" / "FiveM Enhanced" / "RedM"). The saved-servers rows are `SavedServerItem` (name/address/steam/discord + enrichment state `CfxId`/`HasCfxId`/`Online`/`Players`/`MaxPlayers`/`StatusLabel` (`players/max`, `OFFLINE`, `UNRESOLVED`)/`Game`/`GameTagLabel`/`HasGame`/`Icon` bytes, `ApplyPresence(ServerPresence)`, `SetIcon(byte[])`, `SetCfxId(string)`); `ServerPresence` now carries a nullable `GameClient` (from the catalog `gamename` var) so rows render the per-game tag, plus the catalog-published `IconVersion` that drives the direct icon path, and `ApplyPresence` keeps the last known game when a presence carries no game (`ServerPresence.Offline` is the not-in-catalog placeholder); `MainViewModel` owns save-time background CfxId capture for IP:port/domain (`TryCaptureCfxId` → `_enrichment.ResolveCfxIdAsync` → repository `Update`, fire-and-forget, dialog never blocked; CFX-form ids are stored synchronously at `SavedServer.Create` and preserved on same-address edits) and the per-minute `RunEnrichmentLoopAsync(cancellationToken, cadence?, delay?)` that applies presence + icons to rows with a CfxId and leaves null-CfxId rows plain (`RefreshServerInfoAsync(forceRefresh, cancellationToken)`: the token is honored at entry and per row, and the loop re-checks between the server-info and status refreshes, so a closed window never runs one final cycle; rows whose presence publishes an `IconVersion` get the icon via the direct `GetIconAsync(id, version)` path — the loop never probes `/single/`, and rows without one are skipped; outage → no update, never throws; the loop swallows a throwing refresh so one bad cycle never kills it). The manual-refresh cooldowns (saved list + browser) ride the same window-close token through the shared `ViewModels/Cooldown` helper (the composition root owns one CTS cancelled on `window.Closed`).
- `Service/CfxService.cs`: queries `https://frontend.cfx-services.net/api/servers/single/{cfxId}`; typed vars include `sv_enforceGameBuild`, `sv_pureLevel`, `sv_defaultGameBuild`, `sv_replaceExeToSwitchBuilds`, `sv_poolSizesIncrease`, `sv_enforceSteamAuth`, `gamename`, `requestSteamTicket`.
- `Service/ServerCatalog.cs` (seam): downloads + caches (TTL) the streamRedir catalog (protobuf frames via `Service/ServerCatalogDecoder` + `Proto/master.proto` codegen); answers `LookupByIpPortAsync`/`LookupByEndPointAsync` and `GetSnapshotAsync` (returns `IReadOnlyList<Master.Server>?`, null on outage vs empty list; `GetServersAsync` = `GetSnapshotAsync() ?? []`) with single-flight: concurrent callers (connect, enrichment loop, browser) share one in-flight download behind a gate that owns both cache fields and the fetch task, so the cache write is coherent with every read (a forced refresh joins an in-flight fetch too — it is fresher than any cache could be). `LookupByEndPointAsync` (match by cfx id) is currently used only by tests but stays as part of the catalog seam contract, ready for future id-based lookups. Never throws on outage/corruption — returns no match. In catalog frames `EndPoint` is the canonical cfx id; in `/single/` responses it is a connection endpoint.
- `Service/CfxVars.cs`: shared variable mapping (`gamename`→`GameClient` via `TryGetGameClient`, ints via `TryGetInt`, strict `"true"`/`"false"` booleans via `TryGetBool`, raw strings via `TryGetString`, `requestSteamTicket` via `MapSteamTicket`) used by `CfxService` and `ServerResolver`. It also maps the catalog's typed `iconVersion` proto field (field 11) via `TryGetIconVersion` (zero = no icon; any non-zero value including negative is a valid version) used by `ServerEnrichmentService` and `ServerBrowserItem`.
- `Service/CfxStatusService` (seam, `HttpClient`): downloads `https://citizenfx.statuspage.io/api/v2/summary.json` once per call (no internal cache — the VM's per-minute loop is the throttle) and returns `IReadOnlyDictionary<GameClient, CfxStatus>?` (null on outage/parse failure; swallows `HttpRequestException`/`TaskCanceledException`/`JsonException` only). `CfxStatus` (in `Core/Enums`) = `Operational | Degraded | PartialOutage | MajorOutage | Maintenance | Unknown`; component strings map (`operational`/`degraded_performance`/`partial_outage`/`major_outage`/`under_maintenance`, else `Unknown`) and page `status.indicator` maps (`none`/`minor`/`major`/`critical`, else `Unknown`). FiveM/RedM read their dedicated components (name match first, id return-part); the statuspage publishes **no FiveM Enhanced component**, so FiveMEnhanced reads the page-level indicator instead. `CfxStatusItem` (row VM) holds `DisplayName`/`Status`/`StatusLabel` (`OPERATIONAL`/`DEGRADED`/`PARTIAL OUTAGE`/`OUTAGE`/`MAINTENANCE`/`UNKNOWN`); `CfxStatusToBrushConverter` (green/amber/red/grey, data-only). MainViewModel exposes `FiveMStatus`/`FiveMEnhancedStatus`/`RedMStatus` + ordered `CfxStatuses`, `RefreshCfxStatusAsync` applies a non-null map (null keeps last known; first-ever failure → `Unknown`), called once in `InitializeAsync` and each `RunEnrichmentLoopAsync` cycle. The hardcoded `FIVEM / CFX  ONLINE` block is replaced by a three-row ItemsControl bound to `CfxStatuses`.
- GitHub auto-update (v1.3; delivered state in the v1.3 bullet): three contracts a caller must not weaken — `IReleaseFeed.CheckForUpdateAsync() → LauncherUpdate?` (`Service/GitHubReleaseFeed`; never throws, null covers no-update/outage/unpublishable), `IUpdateApplier.ApplyAsync(update) → Task<bool>` (`Launch/UpdateApplier`; true = relaunch handed off and exit invoked, false = running exe untouched and still running), and `MainViewModel`'s optional both-or-none nullable ctor pair (unwired = the whole feature off). `Core/AppVersion.TryParseTag` owns tag syntax; `System.Version` owns comparison.
- `Service/IRequirementReadiness` (seam): `Task<bool> IsRunningAsync(ExternalApp)` (coarse "process exists" gate) and `Task<bool> IsReadyAsync(ExternalApp)` (the gate the preparer/connect flow wait on). Real `Service/ProcessReadinessChecker` checks process names via an injectable `Func<string,bool>` (default real lookup via `Service/ProcessProbe.AnyRunning`, which disposes every `Process` instance `GetProcessesByName` returned — the readiness poll leaked native handles before); mapping `ExternalApp.Steam`→`steam`, `ExternalApp.Discord`→`Discord`. `IsReadyAsync` for Steam is the **composite probe**: `steam` process AND `steamwebhelper` process (both through the process seam) AND a logged-in session — `ActiveUser` from `HKCU\Software\Valve\Steam\ActiveProcess` read via an injectable `Func<int?>` (default real registry, same seam pattern as `ClientInstallLocator`); Discord ready = running; missing/throwing probe or registry → false, never throws. This deliberately does NOT equate "process running" with "Steam fully loaded/logged in".
- `Service/IClientInstallLocator` (seam): `Task<bool> IsInstalledAsync(GameClient)`, `Task<string?> GetExecutablePathAsync(GameClient)`, `Task<string?> GetInstallDirectoryAsync(GameClient)` (dir only when installed). Real impl `Service/ClientInstallLocator`: Legacy FiveM install dir resolves from the registry `HKCU\Software\CitizenFX\FiveM` -> `Last Run Location` first (injectable `Func<string?>` seam, default real registry) with `%localappdata%\FiveM\FiveM.app` fallback, and counts as installed when `FiveM.exe` exists inside the `.app` dir or as its direct sibling (portable/zip layout); Enhanced probes `%localappdata%\FiveM for GTAV Enhanced\FiveM.exe` directly (no `.app` subfolder); RedM mirrors the Legacy pattern with `HKCU\Software\CitizenFX\RedM` -> `Last Run Location` and the `%localappdata%\RedM\RedM.app\RedM.exe` fallback. Both Legacy-like branches share `ResolveAppStyle(localAppData, provider, folderName, exeName)`. Never test the real OS install (seams replace filesystem and registry calls).
- `Service/ICitizenFxConfigWriter` (seam) + `Service/CitizenFxConfigWriter`: read-modify-write of `[Game]` keys in `CitizenFX.ini` — creates the file when absent, preserves every other key/section verbatim, only rewrites when a target value differs, and rejects (skips) any entry whose key or value contains a line break *before any I/O* so a server-published `sv_poolSizesIncrease` can never inject keys/sections into FiveM's config (a poisoned entry degrades the write — it is skipped, so a previous value may persist until the next clean connect).
- `Domain/ServerResolver.cs`: resolves the four address forms; `IpPort`/`DomainPort` degrade to a connectable unvalidated profile when not published in CFX (or on DNS/catalog failure). `IDnsResolver` is the DNS seam.
- `ConfigurationRepository` and `ServerRequirementsResolver` are intentional seams per `docs/adr/0001-intentional-middle-men-seams.md` (do not inline without reopening that ADR).
- `Domain/ServerAddress` owns the `cfx.re/join/<id>` form and address classification/validation (`ServerAddressKind`, `Classify`, `ExtractCfxId`, `HasServerFormWithNonEmptyId`), reused by `ServerResolver` and `FiveMLaunchOptions`.
- Keep business logic out of XAML code-behind and out of real processes/filesystem so tests stay fast.

## Hard design constraints (from DOC.md)
- RSC is never managed by the launcher. Steam/Discord are per-server `ServerProfile` requirements, never universal.
- Server-published (CFX) requirements win over manual config when connecting; Dev Mode build/pure overrides apply only when opening FiveM directly; one carve-out: a saved server's manual `Requires Steam = true` is additive and always requires Steam, even when the server publishes `sv_enforceSteamAuth = false`. Second carve-out (v1.2): a **loopback** saved server (`localhost`/`127.0.0.1`, any port form — `ServerAddress.IsLoopbackAddress`) may carry manual connection parameters (`CfxId`, `GameBuild`, `PureMode`, `GameClient` on `SavedServer`, entered in the dialog's loopback-only section): a resolvable manual cfx id wins over the manual values (its published build/pure/game apply, `IsCfxValidated = true`); a delisted id or no id applies the manual values; the connect address is ALWAYS the direct loopback address, never the join form.
- Never equate "process started" with "service ready/authenticated".
